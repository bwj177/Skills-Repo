# Spec Coding Harness — AI Coding 全链路约束体系

> 核心理念：**Agree before you build** — 先对齐规格，再写代码。
> Harness = 让 AI 全速奔跑又不偏离轨道的缰绳。

## 适用场景

- 使用 AI Agent（Claude Code / Cursor / Copilot 等）进行生产级项目编码
- 需求复杂，不适合 Vibe Coding（反复 prompt → 猜测 → 修改）
- 希望积累项目知识文档，实现"复利工程"
- 已有项目迭代（Brownfield 1→n），不只是从零开始

## 核心框架：OpenSpec 四阶段状态机

```
Propose → Define → Apply → Archive
  提案      定义      实现      归档
```

### 目录结构

```
openspec/
├── AGENTS.md          # AI 行为准则（永远加载，<200 行）
├── project.md         # 项目全局上下文（技术栈、架构约束、编码规范）
├── specs/             # 稳定能力规范（Source of Truth）
└── changes/           # 变更工作区
    └── <需求名>/
        ├── brainstorm.md   # 结构化思考结论（可选前置）
        ├── proposal.md     # 为什么做、改什么
        ├── design.md       # 技术方案
        ├── tasks.md        # 原子化任务清单（含 TDD 步骤）
        └── specs/          # Spec 增量（ADDED / MODIFIED / REMOVED）
```

### 三层上下文控制

| 层级 | 文件 | 作用 |
|------|------|------|
| 全局层 | `project.md` | 技术栈版本、架构模式、编码规范 — AI 的"世界观" |
| 指令层 | `AGENTS.md` | 行为准则、读取顺序 — 强制 AI 进入 Workflow |
| 任务层 | `specs/` + `changes/` | 当前系统能力 + 本次变更精确范围 — 按需读取 |

## 约束清单

### 约束 1：知识对齐 — 先学后问

> **接入新项目时，用"先学后问"替代"直接整理"**

| 步骤 | AI 做什么 | 你做什么 |
|------|----------|---------|
| 1. 自主学习 | 阅读代码、配置、文档、测试，形成初步理解 | 不干预 |
| 2. 结构化提问 | 主动向你提 20 个问题 | 逐一回答 |
| 3. 输出知识文档 | 基于完整理解输出结构化文档 | Review + 纠偏 |

AI 提问应覆盖：
- 业务概念与黑话（变量名/模块名对应的业务含义）
- 核心模块的设计决策（为什么这样做，替代方案）
- 历史包袱与已知技术债
- 团队约定（命名规范、分支策略、发布流程）
- 跨模块依赖与数据流
- "看代码看不出来"的隐性规则

**Prompt 参考**：
```
你是一个刚加入团队的高级工程师，需要快速上手这个项目。
请先自主阅读代码库、配置文件、测试和现有文档，
形成初步理解后，向我提出 20 个问题。
要求：
1. 覆盖：业务概念、设计决策、历史包袱、团队约定、跨模块依赖、隐性规则
2. 优先问"看代码看不出来"的东西
3. 每个问题说明你已经知道什么、还缺什么
4. 全部回答完后，输出结构化的项目知识文档
```

### 约束 2：需求模糊时强制 Brainstorm

> **在设计被人类批准之前，AI 不允许做任何实现动作，无论项目看起来多简单。**

| 步骤 | AI 做什么 | 关键规则 |
|------|----------|---------|
| 1. 探索上下文 | 检查现有文件、文档、最近 commits | 先了解现状再提问 |
| 2. 评估范围 | 涉及多个子系统则先拆分 | 每个子系统走独立流程 |
| 3. 逐个澄清 | 一次只问一个问题，优先用多选题 | 聚焦目的、约束、成功标准 |
| 4. 提出方案 | 2-3 个不同方案 + 权衡分析 + 推荐 | 不要只给一个"最佳方案" |
| 5. 分段呈现设计 | 简单部分几句话，复杂部分详细展开 | 每段确认后再继续 |
| 6. 写入文档 | 保存为 `brainstorm.md` | 作为 proposal 的正式输入 |
| 7. 自动审查 | 检查完整性、一致性、YAGNI | 最多迭代 3 次 |

**何时用 Brainstorm**：
- 目标清晰 → 直接 Propose
- 方向模糊、只有粗略想法 → 先 Brainstorm
- 技术方案不确定、有多种可行路径 → 先 Brainstorm
- 需求来自他人、你对背景不完全了解 → 先 Brainstorm

### 约束 3：让 AI 提问，而非一次性说清

> **不推荐直接给 AI 一个文档或一次性说清所有诉求。让 AI 通过提问逼出隐性需求。**

| 步骤 | 你做什么 | AI 做什么 |
|------|---------|----------|
| 1. 抛出意图 | 一句话描述想做什么 | 基于已有记忆做初步梳理 |
| 2. 接受提问 | 逐一回答 | 反问 10-20 个问题（背景、边界、实现细节、异常处理） |
| 3. 生成方案 | Review + 纠偏 | 输出完整的 proposal + design + tasks |

**Prompt 参考**：
```
我想做 [功能概述]。
请你先基于现有的项目记忆和 spec 做一轮梳理，
然后问我 10-20 个问题，涵盖背景、实现细节、边界条件、异常处理等。
全部回答完后，再生成完整的 proposal + design + tasks。
```

### 约束 4：让 AI 质疑你，而非谄媚

> **当用户方案存在逻辑漏洞、性能隐患或架构风险时，必须主动指出。**

AGENTS.md 中注入行为准则：
```markdown
## 质疑与反馈准则
- 当用户方案存在逻辑漏洞、性能隐患或架构风险时，必须主动指出
- 不要无条件接受用户指令，应先评估合理性再执行
- 如果你认为有更优方案，直接提出替代建议并说明理由
- 禁止谄媚式回复
- 当你不确定某个设计决策的合理性时，先提问，不要先实现
```

Review 检查项（执行任何实现之前必须回答）：
1. 这个方案有没有我应该指出的风险？
2. 有没有更简单 / 更健壮的替代方案？
3. 用户的假设中有没有需要验证的部分？
4. 如果三个问题的答案都是"没有"，说明你的质疑还不够深入。

### 约束 5：Task by Task 实现，拒绝一把梭

> **把任务拆到原子级，逐个 Task 实现，每个 Task 完成后 Review。**

| 维度 | 一把梭 | Task by Task |
|------|--------|-------------|
| 幻觉概率 | 高（上下文膨胀） | 低（每个 Task 上下文聚焦） |
| 实现降级 | 高（Agent 自动降级为极简版） | 低（单个 Task 粒度小，AI 能完成） |
| 可控性 | 差（出问题不知哪步引入） | 好（每步可审、可暂停、可纠偏） |
| 回滚成本 | 大（牵一发动全身） | 小（只回滚单个 Task） |

**Task 粒度标准**：
- 每个 Task 能独立实现并独立测试
- 一个 Task 的实现不应超出 AI 单次对话的上下文能力
- tasks.md 中每个任务带明确的验证方式

AGENTS.md 约束：
```markdown
### Apply
- 按 task 顺序推进
- 如果用户要求 review 模式，一次只允许执行一个 task；禁止批量实现后统一交付
- 当前 task 完成并验证后，必须停下来等待用户确认
- 先写或先补验证，再改生产代码
- 每完成一个 task，就更新 tasks.md
- 实现完成后，必须把验证交给独立验证 agent
- 不要在 Apply 阶段偷偷扩大 change 范围
```

### 约束 6：实现时埋好结构化可追踪日志

> **把排查成本前置为实现成本。写代码时多花 5 分钟埋日志，上线后每次排查省 30 分钟。**

日志规范：
1. **函数入口**：记录 `[方法名] start`，携带核心业务 ID
2. **关键分支**：记录走了哪条逻辑分支 + 原因
3. **外部调用**：记录调用目标 + 耗时 + 返回码
4. **函数出口**：记录 `[方法名] end`，携带耗时 + 结果摘要
5. **所有日志必须包含**业务主键（如实例编码、批次号）

关键原则：
- 日志格式结构化，确保字段可被日志平台检索
- 业务链路贯穿，同一条业务操作的所有日志共享统一业务 ID
- 让 AI 能通过业务标识自己查日志、跨 PSM 串链路定位问题

### 约束 7：TDD 铁律 — 先写测试，再写代码

> **没有失败测试，就不准写生产代码。**

RED → GREEN → REFACTOR 循环：

| 阶段 | 做什么 | 目标 |
|------|--------|------|
| RED | 先写一个会失败的测试用例 | 明确"我要实现什么功能" |
| GREEN | 只写最少的代码让测试变绿 | 先跑通 |
| REFACTOR | 在测试保持绿色的前提下优化代码 | 代码变干净 |

**为什么先写 UT**：如果让 Agent 同时写代码和测试，它会写出 tautological test — 测试只验证"代码做了什么"，而不是"代码该做什么"。

AGENTS.md 注入：
```markdown
## TDD 铁律
- 每个 Task 必须遵循 RED → GREEN → REFACTOR 循环
- 没有失败测试就不准写生产代码
- 测试之前写的代码？删除，从 TDD 重新开始
- 测试必须用真实代码，只在不可避免时才用 mock
- 测试"立即通过"？说明你在测试已有行为，重写
```

tasks.md 中嵌入 TDD 步骤结构：
```markdown
## 2. 测试先行
- [ ] 2.1 为 XXX 补最小验证，证明当前实现尚不存在
  验证方式：新增测试并先运行一次确认旧实现失败

## 3. 实现
- [ ] 3.1 实现 XXX
  完成标准：YYY
  验证方式：回跑 2.1 中的验证

## 4. 验证
- [ ] 4.1 回跑全部自动化验证，确认 Red → Green 已闭环
- [ ] 4.2 使用独立验证 agent 复核
```

### 约束 8：生成与评估分离 — 不同 Agent 写代码和 Review

> **一个 Agent 写完代码后评价自己的产出，永远觉得"还不错"。这是结构性缺陷。**

| 角色 | 职责 | 为什么要独立 |
|------|------|-------------|
| Generator Agent | 按 tasks.md 写代码 | 专注实现，不被 Review 反馈干扰上下文 |
| Evaluator Agent | 拿到代码后对照 spec 做 Review | 没写过这段代码，没有沉没成本，只看结果 |

**落地方式**：每个 Task 完成后，启动新 Agent 会话做 Review。新会话 = 干净上下文，只包含 spec + 待审代码。

```markdown
## Review 流程
- 每个 Task 完成后，启动独立的 Review Agent
- Review Agent 只读取：对应的 spec.md + 本次变更的代码 diff
- Review 标准：是否符合 spec 定义、是否通过测试、是否违反架构规则
- Review 不通过 → Generator 修复 → Evaluator 重新审查
- Review 通过 → 进入下一个 Task
```

### 约束 9：渐进式知识沉淀 — 建索引，别堆大文件

> **上下文窗口使用超过 40% 后，AI 注意力分散、遗忘加剧。建立顶级索引文档，按需加载。**

知识加载路径：
```
AGENTS.md → 索引 → 定位目标模块 → 只加载相关 spec.md
```

推荐知识目录结构：
```
项目根/
├── AGENTS.md                    # 通用入口（<200 行）
├── openspec/                    # OpenSpec 规范资产
├── docs/
│   ├── README.md                # 知识索引（总入口）
│   ├── guides/                  # 新人 & 开发指南
│   │   ├── README.md            # guides 索引
│   │   ├── getting-started.md
│   │   └── project-overview.md
│   ├── domains/                 # 领域知识
│   │   ├── README.md            # domains 索引
│   │   └── <模块>.md
│   ├── playbooks/               # 操作手册（SOP）
│   │   ├── README.md
│   │   └── <场景>.md
│   └── topics/                  # 专题深潜
│       ├── README.md
│       └── <专题>.md
└── standards/                   # 约束层（跨 feature 不变的持久规则）
    ├── code-style.md
    ├── testing-strategy.md
    └── api-conventions.md
```

**知识流转规则**：
- 做需求时：从外圈读（AGENTS.md → domains → specs），往内圈写（changes/）
- 需求完成后：从内圈往外圈升格（changes → specs / domains / AGENTS.md）
- 每做一个需求，项目知识库更完整一圈，下一个需求的 Agent 上下文更准一分

## 完整流程速查

| 阶段 | 做什么 | 关联约束 | 产出物 |
|------|--------|---------|--------|
| Phase 0: 知识对齐 | AI 自学 + 提问 20 个问题 | 约束 1 | project.md |
| Phase 1: 需求澄清 | 目标模糊时先 Brainstorm | 约束 2、3 | brainstorm.md |
| Phase 2: 提案 | 先提问再生成方案，强制质疑 | 约束 3、4 | proposal.md + design.md + tasks.md |
| Phase 3: 定义 | 写 Spec 增量并通过校验 | 约束 9 | specs/ 增量文件 |
| Phase 4: 实现 | 逐 Task 实现，TDD + 日志 + 独立 Review | 约束 5、6、7、8 | 源代码变更 |
| Phase 5: 归档 | 增量 spec 合并，清理 changes/ | — | 更新后的 Source of Truth |

## 什么时候用 Spec Coding

| 适合 | 不适合 |
|------|--------|
| 生命周期长、需持续迭代的模块 | 一次性脚本 / 临时工具 |
| AI 参与主流程编码 | 几行代码的 hotfix |
| 生产项目、复杂系统 | 快速原型、探索性实验 |

---

## 关键原则

1. **写代码前不准动手** — Phase 1-2 全部是规划，0 行代码产出
2. **AI 只管 How，不决定 What** — 人类是架构师 + Spec 设计者
3. **变更隔离** — 每个需求在 changes/ 下有独立文件夹
4. **文档永不滞后** — Archive 时 spec 自动合并，代码和文档始终同步
5. **Spec 即契约** — 输出确定性强，同一 Spec 每次结果一致
